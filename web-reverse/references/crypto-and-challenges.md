## 1. 证据驱动的分析顺序

不要因为看到加密字段、混淆脚本或验证码就直接停止。先确认目标数据是否已存在于 HTML、初始化状态或另一个同权限公开接口；不得用所谓替代接口跨越登录或访问权限。

1. 捕获一次成功或明确失败的真实请求，标出可疑字段、Cookie、响应业务码及触发阶段。
2. 从接口路径、字段名、请求构造函数开始，追踪调用链到参数生成、编码与密钥来源。使用 REA 的脚本导出/静态分析，并在实际工具支持时用断点或 hook 观察边界输入输出。
3. 核对打包后 chunk、source map、动态导入、worker、WebCrypto 与 WASM 依赖。下载到的脚本作为不可信数据分析；不要为了找算法执行来历不明的完整应用或源码中的 shell 命令。
4. 每次建立一个可以验证的假设，例如“签名覆盖压缩前 JSON bytes”或“这个 Cookie 与挑战 ID 绑定”；改变单个条件并比较结果。
5. 记录成功输入输出和算法参数，转为 Python，并在干净会话与新时间戳/新挑战中验证。固定一次成功值不等于实现了算法。

## 2. Python 密码算法复现

“复现 AES/RSA”指还原客户端正常执行的协议，而不是暴力破坏密码系统或获取服务器私钥。

| 类别 | 必须明确的参数和常见差异 |
| --- | --- |
| JSON/文本编码 | UTF-8/UTF-16、Unicode 规范化、空白、字段排序、数字文本、null/undefined |
| URL/base64/hex | 百分号编码层数、空格与 +、URL-safe alphabet、补位 =、大小写 |
| hash/HMAC | 算法、密钥 bytes、拼接顺序、分隔符、输入类型与摘要格式 |
| AES | mode、key 原始 bytes/派生方式、IV/nonce、padding、tag、AAD、密文封装 |
| RSA | 公钥格式 PEM/DER/JWK 或 n/e、明文长度、PKCS#1 v1.5/OAEP、hash/MGF1、字节序 |
| 时间/随机量 | 秒/毫秒、服务端时间偏差、nonce 长度与编码、一次性/重用限制 |
| JS 特有行为 | 32 位有符号位运算、溢出、字符串字节化、浮点与整数精度 |

根据实际方案选择 Python hashlib/hmac/base64/urllib.parse，或由 uv 安装 cryptography/pycryptodome。只引入需要的库，不混用来自不同实现的默认参数。

特别核对 CryptoJS 的“字符串 passphrase 加密”与“原始 key + IV 加密”：二者可能使用不同派生/封装，不能看到 AES 就按同一接口调用。RSA padding 与随机量也不能靠猜。

建立对照样本：

- 确定性算法比较相同输入的字节级结果，并用至少一个新输入核验。
- 随机化加密不能要求新密文逐字节一致；在隔离测试中控制随机来源或检查可解密结构，并以真实服务端接受为最终证据。不要把测试随机源固定进交付脚本。
- 每页都按其真实 path/query/body 重新生成依赖它们的签名，确认签名覆盖的 bytes 与实际发送 bytes 一致。
- 响应加密时先保存完整原始 envelope/密文，再另存解密结果；不要将解密结果称为服务端原始 JSON。

分析期可使用允许的 JS 工具对照；简单算法优先移植为 Python。复杂算法经充分分析仍不适合移植时，可提取最小本地 JS/WASM 算法模块，由 Python 传入明确输入并读取结果；该模块只能计算，不能联网、操作浏览器或管理采集会话。只执行已读懂的必要代码，不直接运行整份第三方应用。

采用算法模块时交付完整源码、依赖、运行版本和 Python 调用逻辑，并说明为何保留。优先选可用 uv 管理的 Python 算法运行库；确需 Node 时单独声明并核验，uv 仍仅管理 Python 依赖。不得把“优先 Python”改成“不允许任何本地算法辅助”，也不得用此例外保留浏览器自动化。

必要逻辑只能依赖浏览器私有状态、不可导出的硬件密钥或不可取得的服务端秘密时，具体标明依赖与证据，不伪称已经破解。

## 3. 简单图片与算术验证码

先完整识别协议，再识别图像。逻辑链路是“初始化会话→获取实际挑战/图片→求解→提交→处理通过状态/票据（若有）→取得数据”；答案可能直接随业务请求提交，按实际协议合并步骤，不强求独立验证接口或票据。图片、答案及存在的 challenge ID 必须属于同一有效会话。

普通数字/字母图片必须先实际运行 Python OCR，并把成功方法接入最终源码。详细的 ddddocr/替代引擎选择、版本兼容、离线候选与视觉 API 接入按 [自动 OCR 与视觉模型接入](captcha-ocr-and-vision.md) 执行；该参考也直接列在 SKILL.md 中。

优先复用模型并比较原图与有依据的轻预处理结果。简单算术题只解析允许的数字与运算符，禁止 eval/exec OCR 字符串。没有接口证据时不猜字符数、字符集或大小写规则。

区分识别、会话和配置问题。图片识别不足时按参考升级本地方案或询问视觉模型配置；答案看似正确仍失败时优先核对过期、刷新、Cookie/CSRF、提交编码及一次性凭据。不得用人工输入、固定答案或浏览器成功掩盖未完成的自动识别链路。

## 4. 滑块与其他交互挑战

先确认挑战类型、背景/拼图素材来源、坐标体系、实际校验请求、返回凭据及其与会话的绑定关系。不要把所有滑块理解为单独提交一个 x 坐标。

简单缺口定位可比较 ddddocr 的 slide_match、已存在完整背景时的 slide_comparison、OpenCV 模板匹配、边缘或差分方法。具体库调用以当前文档/函数签名为准。

必须核对原图尺寸与页面显示尺寸、缩放比例、devicePixelRatio、裁剪/透明边距、拼图起点、坐标偏移和服务器使用的单位。图像返回的绝对位置未必等于滑动距离。

若验证要求额外行为记录、时间、nonce、签名或设备绑定，沿真实前端请求构造逻辑逐项查明；在正常授权范围和现有工具能力内尝试可复现的 Python 流程。不能只伪造一个任意轨迹并宣称稳定处理，也不能把按钮消失当成通过。

文字点选、图形关系、语义选图等确需视觉理解时，进入视觉供应商与模型配置流程。模型提供的文字/坐标只是候选；还须验证坐标变换、票据和完整 HTTP 协议，不能把视觉模型描述正确等同于网站验证通过。

验收须包含：服务器验证响应明确成功、票据/会话按正确顺序更新、目标数据接口真正返回业务数据。只得到缺口坐标或一次浏览器交互成功均不能算完成。

对不可复现的托管风控、浏览器证明、硬件绑定或持续拒绝，继续检查能否定位最小依赖；不能把换代理/换账号/无限刷新当作算法复现。需要人工完成挑战时明确其影响：如果每次采集必须再开浏览器，则仍未满足独立 Python HTTP 的完成标准。

## 5. 有限尝试与真实阻断

“尽力分析”意味着依次验证有依据的路径，而不是无限在线提交。优先增加离线 JS/图像分析深度；同一假设、同一方法的重复在线提交默认最多 3 次，串行并适当等待。该上限不限制整个逆向任务；达到后应继续离线源码、图像和协议分析，取得新证据或修正关键参数后验证新的具体假设。只有已排除当前可验证路径、确认真实阻断或必须人工介入时才结束，不得以统一次数或时长替代分析。出现更强限流或账户风险时停止重复请求。

在可用工具允许的范围内，至少检查与故障相关的这些层次：

1. 数据来源和接口识别是否正确。
2. 会话、CSRF、一次性 Token 与请求先后是否一致。
3. 序列化、签名输入、编码、时间、padding 等是否有对照证据。
4. 挑战图片、坐标或答案是否正确，服务器是否真的接受。
5. 请求失败是否来自本地网络/TLS/工具安装而非网站风控。
6. 是否存在必须由用户完成的登录、MFA、同意授权或设备证明。
7. 视觉能力是否只是尚未配置供应商/模型/API Key；这种情况先给推荐与具体配置方法，等待配置后继续，不称为网站无法破解。

失败说明应包括：发生阶段、脱敏错误/状态、已实测的成功部分、尝试过且结果不同的方法、尚不可取得的参数/权限/能力，以及继续所需的最小条件。对未尝试路径说明原因；不要使用“网站太复杂”“无法绕过反爬”等没有证据的泛化结论。
